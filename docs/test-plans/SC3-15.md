## 作る API

| API | できる人 | すること |
| --- | --- | --- |
| `POST /api/matrix/ecus/{ecu_id}/review`（確認完了・修正依頼） | メーカーの確認者 | 最新の承認済みの版の確認状況を「確認完了」か「修正依頼中」にする。修正依頼は理由が必須で、理由は種類「修正依頼」のコメントとして残す。承認済みの版がなければ 409。すでに確認済み・修正依頼中なら 409 |
| `GET /api/ecus/{ecu_id}/comments` | その ECU のサプライヤの全員、メーカーの確認者・システム管理者 | 最新の承認済みの版のコメントを、スレッド（質問と回答）の形で返す。自分にとって未読かも返す |
| `POST /api/ecus/{ecu_id}/comments` | 質問：メーカーの確認者。回答：その ECU のサプライヤの承認者（仕様の役割の表） | 質問（ECU 全体か対策項目ごと）、回答（質問のスレッドに付ける）。状態は変えない |
| `POST /api/ecus/{ecu_id}/comments/read` | 読める人 | その ECU のコメントを全部既読にする |

- 会社の絞り込み：サプライヤは自社の ECU だけ（他社と存在しない番号は 404）。メーカーは全部の ECU。この「どちらも通る」入口は新しい依存（`visible_ecu`）として作り、権限の表に「サプライヤ用」「メーカー用」のほかに「両方」の種類を足す
- 回答の親は、同じ ECU の同じ版の質問だけ（DB の複合の外部キーで守っている。API でも先に確かめて 422）
- すべての確認・コメントを監査ログに残す（守りの決まり5）。コメントの本文は監査ログに入れない
- 本文の長さの上限（例 2000 文字）、空白だけは 422（DB の制約もある）
- 一覧（サプライヤ）とマトリクス（メーカー）に、未読の件数を出す

## 作る画面

- ECU 詳細：コメントのスレッド、質問（メーカー）・回答（サプライヤの承認者）の入力、開いたら既読にする
- マトリクス：行ごとに「確認完了」「修正依頼」（理由の入力）、未読の件数
- 自社 ECU 一覧：未読の件数、修正依頼中の表示

## テスト

| # | 確かめること |
| --- | --- |
| 1 | 確認完了：承認済みの版の確認状況が「確認完了」になり、確認者・日時が入る。マトリクスに出る |
| 2 | 修正依頼：理由が必須（なし・空・空白だけ・長すぎる → 422）。確認状況が「修正依頼中」、理由がコメントに残る。承認済みの版がない・すでに確認済みなら 409 |
| 3 | 修正依頼から新しい版：上の完了条件の流れ |
| 4 | 質問：ECU 全体・対策項目ごとに作れる。確認者以外（サプライヤ・システム管理者）は 403 |
| 5 | 回答：その ECU のサプライヤの承認者だけ。親が質問でない・別の版・別の ECU のコメントなら 422 |
| 6 | 他社：B 社の全部の役割で、A 社の ECU のコメントの取得・投稿・既読は 404（存在しない番号と同じ応答）。権限の表のテストで自動でかかる |
| 7 | 未読：相手のコメントは未読、自分のは既読。既読にしたら未読の件数が 0。人ごとに別 |
| 8 | 監査ログ：確認・修正依頼・質問・回答で残る。断られた操作では増えない |

## 確認の API と守りの決まり7（2026-11-28 にオーナーが決めた：下の確かめ方でよい）

- 確認の API（`POST /api/matrix/ecus/{ecu_id}/review`）はメーカー用で、メーカーには全社の ECU が見える（仕様）。メーカーにとって「他社のデータ」はないので、「他社のユーザーで呼んで 404」は当てはまらない
- 代わりに、サプライヤ（他社の B 社を含む）は ECU を探す前に 403 にし、他社の ECU でも存在しない番号でも、状態・本文・Content-Type が同じ 403 になることを権限の表のテスト（項目3・項目5）で確かめる。存在は漏れない
- 403 にしてよいのはメーカー用の API だけ、というテストも置く（サプライヤ用の API で 403 を返すと存在が漏れる。決まり2）
- コメントの API（次の PR）は、サプライヤとメーカーの両方が呼ぶので、他社のサプライヤには 404 にする（決まり7のとおり）
