# テストの一覧：SC3-8（Day 2 テーブル設計・Alembic・ダミーデータ）

完了条件：全テーブル（`docs/spec.md` の9つ）にデータが入る。

テストは手元の PostgreSQL（docker compose）に、テスト専用の DB（名前が `ecu_sec_test` で始まるものだけ）を作り直して流す。開発用の DB `ecu_sec` には触らない（名前が違えば準備の段階で止める）。**制約のテストは、Alembic の変更履歴で作った DB に対して流す**（モデルからは作らない。Alembic の自動比較は CHECK 制約の差を見つけられないため）。

DB の制約は**二重の守り**。Phase 4 の DynamoDB には CHECK も一意の制約もないので、同じ決まりを API でも守り、API のテストを入れる（Day 7・8・10）。

## DB で守る決まり（制約にはすべて名前を付け、テストは名前で確かめる）

- 状態は文字列＋CHECK 制約（PostgreSQL の ENUM 型は使わない）
  - assessments.status：draft・pending・rejected・approved
  - assessments.review_status：unreviewed・confirmed・change_requested
  - assessment_entries.status：done・in_progress・not_done・not_applicable
  - comments.kind：question・answer・change_request
  - companies.type：oem・supplier
  - users.role：sys_admin・reviewer（メーカー）、supplier_admin・editor・approver（サプライヤ）
- 状態ごとに必須の列
  - pending・rejected・approved：submitted_by・submitted_at が必須
  - approved：approved_by・approved_at・review_status が必須。approved 以外は approved_by・approved_at・review_status が空
  - review_status が confirmed・change_requested：reviewed_by・reviewed_at が必須。unreviewed または空：両方とも空
- 職務分離：approved_by ≠ submitted_by（承認済みなら両方必須なので、空にしてすり抜けられない）
- 差し戻し：rejected なら reject_reason が必須で、空白（全角の空白を含む）だけではいけない
- 版：(ecu_id, version) は一意、version は1以上。作業中の版（draft・pending・rejected）は1つの ECU に1つまで（部分一意索引）
- 入力：(assessment_id, item_id) は一意。done・not_applicable なら planned_date は空
- コメント：本文は空白だけではいけない。answer は親（parent_id）が必須、question・change_request は親なし。親は同じ版のコメント（複合の外部キー）
- ユーザー：メールは大文字・小文字を区別せずに一意（lower(email) の一意索引）。is_active は必須で既定は true
- 既読：(user_id, comment_id) が主キー
- 外部キーはすべて RESTRICT
