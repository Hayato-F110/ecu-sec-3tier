# テストの一覧：SC3-42（API が CORS を許していないことをテストで見張る）

2026-11-26 にオーナーが承認した設計案。CORS（ブラウザが、別のサイトの画面から API の応答を読むのを許すかの決まり）。

## 根拠

- FastAPI の資料（https://fastapi.tiangolo.com/tutorial/cors/）：CORSMiddleware を入れると「appropriate CORS headers」を応答に付け、事前の問い合わせには「200 or 400」を返す。`allow_origins=["*"]` は、ブラウザの言う認証情報（Cookie など）を伴う通信を許さない。Authorization ヘッダーは `allow_headers` しだいで送れるので、守りの本体は「ほかのサイトが応答（トークンを含む）を読めない」こと
- Starlette の公式サイトは 11/26 に名前の解決に失敗して読めなかった。代わりに手元の Starlette 1.10.0 のソースで確かめた：`starlette/middleware/cors.py:41・115・176` で `Access-Control-Allow-Origin` を付ける、`:142-143` で許されない送り元の事前の問い合わせに 400「Disallowed CORS」

## 完了条件とテストの対応表

| `Origin: https://evil.example` の要求に CORS のヘッダーが付かないことを、pytest で確かめられる | #1・#2 |
| 緩い CORS の設定を足すとそのテストが落ちることを、一度確かめた記録がある | #3（PR に書く） |

## テスト（`backend/tests/test_cors.py`）

| # | 確かめること | 確かめない範囲 |
| --- | --- | --- |
| 1 | 全部の API（ログインを含む。登録された API の一覧から作る）に `Origin: https://evil.example` を付けて呼ぶと、応答に `Access-Control-` で始まるヘッダーが1つもない（ログインした A 社の入力者のトークン付きでも） | ブラウザの動き（ヘッダーがなければブラウザは応答を読ませない。これは仕様） |
| 2 | 全部の API に、事前の問い合わせ（`OPTIONS`、`Origin`・`Access-Control-Request-Method: その API のメソッド`・`Access-Control-Request-Headers: authorization,content-type`）を送ると、応答に `Access-Control-` のヘッダーがなく、200 にもならない | 405 か 400 かの番号そのもの（今は CORS の設定がないので 405 の見込み。番号は確かめず、「許していない」ことだけを見る） |
| 3 | 赤の確かめ（常に流す）：(a) どの送り元も許す設定（`allow_origins=["*"]`）を足したアプリでは #1 で落ちる。(b) 送り元を絞った設定（`allow_origins=["http://127.0.0.1:8080"]`）では、ほかのサイトへのふつうの応答にヘッダーが付かないので、#2 で落ちる（#2 の確かめが働いていることの確かめ） | ― |

API の一覧が空なら落ちる（空で通らない）。書き込みの API には通る形の本文を送り、入力の誤り（422）で処理の前に返らないようにする。

## 確かめない範囲（理由）

- ログインが成功したときの応答（パスワードの準備が要るため。失敗の応答は処理まで届く形で確かめる）
- nginx の層：nginx が CORS のヘッダーを足しても、このテストでは気づけない。nginx のテスト（`tests/web/`）は3層が動いているときだけ流れるため、ここでは扱わない（`/code-review` の指摘。足すかはあとで決める）
- `/docs`・`/openapi.json` など、`/api/` で始まらないパス

## 変えるもの

- テストだけ（`backend/tests/test_cors.py`）。アプリのコードは変えない
- 守りに関わる（CI の検査ではないが、公開範囲に関わる）ので、`/code-review` は2回まで
