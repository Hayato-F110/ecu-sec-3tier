## 作る API（どれも URL は ECU の番号で、その ECU の作業中の版に対して行う）

| API | できる人 | 状態の条件（違えば 409） | すること |
| --- | --- | --- | --- |
| `POST /api/ecus/{ecu_id}/submit`（承認申請） | 自社の入力者 | 作業中の版が下書き | 承認待ちにする。申請者・申請日時を**必ず今の人・今の時刻に書き直す**（SC3-25） |
| `POST /api/ecus/{ecu_id}/approve`（承認） | 自社の承認者。申請者本人は 403 | 作業中の版が承認待ち | 承認済みにする。承認者・承認日時、確認状況を「未確認」にする |
| `POST /api/ecus/{ecu_id}/reject`（差し戻し） | 自社の承認者。申請者本人は 403（下の決めてほしいこと1） | 作業中の版が承認待ち。理由が空・空白だけなら 422 | 差し戻しにして、理由を残す |

- 調べる順番：401 → 会社の種類と役割（403）→ 自社の ECU か（404）→ 操作の役割（403）→ 本文の形（422）→ 状態（409）→ 職務分離（403）
- どれも監査ログに残す（`submit`・`approve`・`reject`。対象は `assessment:<版の id>`。差し戻しの理由は監査ログに入れない）
- 同時の操作は、保存と同じく版を行ロック（`with_for_update`）してから状態を確かめる
- DB の制約（申請者≠承認者、差し戻しの理由、承認の欄）は Day 2 で入っている。API はその前に同じ確かめをして、409・403・422 を返す（DB の制約違反を 500 にしない）
- SC3-13 のレビューで先送りにした直し（POST の API が初めて増えるため）：`test_auth.py` の呼び方を表の `method` と `url` から作る。#6（問い合わせの値の書き換え）を表の GET の行の全部で、#8(a)（本文の書き換え）を本文を持つ行の全部で回す
- 3つの API は権限の表（SC3-13）に行を足す。URL に番号を持つので、他社のデータは 404 のテストが表から自動でかかる

## 決めたこと（2026-11-26、オーナーがおすすめどおりに決めた）

1. **差し戻しも、申請者本人はできないことにするか**。おすすめ：できないことにする。理由：自分で差し戻して直すのは、下書きに戻すのと同じで、承認者の確かめを経ないため。仕様は承認だけを書いている
2. **SC3-25 のテストの X・Y**：ダミーデータでは、1つの会社に入力者は1人だけ。テストの中で2人目の入力者を作り、さらに「承認者の役割で承認しようとする」には、X・Y が承認者でもある必要がある。今の役割は1人1つ。おすすめ：テストの中で「入力者 Y」と「承認者 Y'」のように、**同じ人が2つの役割を持てないので、職務分離は『申請者の番号＝承認者の番号』の比べ方で確かめる**（承認者の役割の人が、自分の番号で申請された版を承認しようとする形をテストの中で作る）。または、1人が複数の役割を持てるように仕様を変える（範囲の変更になるので、おすすめしない）
3. **申請のときに、全部の項目が入力済みであることを求めるか**。おすすめ：求める（未入力のまま承認されると、メーカーのマトリクスに空のセルが出る）。仕様には書いていない
