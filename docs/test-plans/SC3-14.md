## 作る API（どれも URL は ECU の番号で、その ECU の作業中の版に対して行う）

| API | できる人 | 状態の条件（違えば 409） | すること |
| --- | --- | --- | --- |
| `POST /api/ecus/{ecu_id}/submit`（承認申請） | 自社の入力者 | 作業中の版が下書き | 承認待ちにする。申請者・申請日時を**必ず今の人・今の時刻に書き直す**（SC3-25） |
| `POST /api/ecus/{ecu_id}/approve`（承認） | 自社の承認者。申請者本人は 403 | 作業中の版が承認待ち | 承認済みにする。承認者・承認日時、確認状況を「未確認」にする |
| `POST /api/ecus/{ecu_id}/reject`（差し戻し） | 自社の承認者。申請者本人は 403（下の決めてほしいこと1） | 作業中の版が承認待ち。理由が空・空白だけなら 422 | 差し戻しにして、理由を残す |

- 調べる順番：401 → 会社の種類と役割（403）→ 自社の ECU か（404）→ 操作の役割（403）→ 本文の形（422）→ 状態（409）→ 申請なら全項目が入力済みか（409）→ 承認・差し戻しなら職務分離（403）
- 「DB が変わらない」の確かめは、`test_api_ecus.py:55-67` の `snapshot()` に、`submitted_by`・`submitted_at`・`approved_by`・`approved_at`・`review_status`・`reviewed_by`・`reviewed_at` の7列を足して使う
- どれも監査ログに残す（`submit`・`approve`・`reject`。対象は `assessment:<版の id>`。差し戻しの理由は監査ログに入れない）
- 同時の操作は、保存と同じく版を行ロック（`with_for_update`）してから状態を確かめる
- DB の制約（申請者≠承認者、差し戻しの理由、承認の欄）は Day 2 で入っている。API はその前に同じ確かめをして、409・403・422 を返す（DB の制約違反を 500 にしない）
- SC3-13 のレビューで先送りにした直し（POST の API が初めて増えるため）：`test_auth.py` の呼び方を表の `method` と `url` から作る。#6（問い合わせの値の書き換え）を表の GET の行の全部で、#8(a)（本文の書き換え）を本文を持つ行の全部で回す
- 3つの API は権限の表（SC3-13）に行を足す。URL に番号を持つので、他社のデータは 404 のテストが表から自動でかかる。approve・reject の自社の ECU は、入力者が申請した承認待ちの DMY-A002（`seed.py:208-213`）を使う（今の `ecu_own` の DMY-A004 は下書きだけで、承認者の期待 200 が 409 になる）。reject の本文は正しい理由を返す関数にする。テストの部品 `Api` に `post` を足す（`api_helpers.py:44-48`）

## 決めたこと（2026-11-26、オーナーがおすすめどおりに決めた）

1. **差し戻しも、申請者本人はできないことにするか**。おすすめ：できないことにする。理由：自分で差し戻して直すのは、下書きに戻すのと同じで、承認者の確かめを経ないため。仕様は承認だけを書いている
2. **SC3-25 のテストの X・Y**：役割は1人1つのまま（1人が複数の役割を持てるようにはしない）。職務分離は「申請者の番号＝承認者の番号」の比べ方で確かめる。作り方は #6・#9 のとおり：API で申請したあと、テストの中でその人の役割を承認者に変えて承認・差し戻しを呼ぶ（2026-11-27、test-plan-reviewer の指摘で #9 の書き方に合わせた）
3. **申請のときに、全部の項目が入力済みであることを求めるか**。おすすめ：求める（未入力のまま承認されると、メーカーのマトリクスに空のセルが出る）。仕様には書いていない

決めたこと1・3は、`docs/spec.md` に日付・決めた人・理由を添えて写す（CLAUDE.md「途中で決めた変更は写しに書く」）。

## 決めたこと（2026-11-27、test-plan-reviewer の指摘から。オーナーがおすすめどおりに決めた）

4. **2回目に差し戻したとき、1回目の理由をどうするか**。おすすめ：上書きして最後の理由だけを残す。理由：理由は「いまの版の状態」の欄で、入力者が見るべきなのは最新の理由だけ。差し戻した事実と日時は監査ログに残る（理由の本文は、他社に見せない欄なので監査ログには入れない決まりのまま）。承認されたあとも、版に残った古い理由は消さない（承認済みの版は上書きしない決まり）が、画面には承認済みの版の理由を出さない
5. **画面が「自分の申請か」を判断する方法**。おすすめ：`GET` の応答に `can_review`（ログインした人がこの版を承認・差し戻しできるか）を API が入れる。理由：画面は申請者の番号と自分の番号を比べる材料を持っていない。比べ方を画面に書くと、API と画面で決まりが二重になり、ずれる。決まりは API の1か所に置く

## 決めたこと（2026-11-27、test-plan-reviewer の2回目の指摘から。オーナーがおすすめどおりに決めた）

6. **申請のときの「入力済み」の意味**（#13）。おすすめ：状態が選ばれている、根拠が空白だけでない、対応中・未対応なら対応予定日がある、の3つ。理由：メーカーのマトリクスに出る内容なので、行があるだけで根拠も予定日もない版が承認されると、一括確認の意味がなくなる
7. **申請・承認の本文の形**（#11）。おすすめ：本文はなくてもよい。`{}` も通す。余計な欄（`submitted_by` など）があれば 422。理由：画面は本文なしで呼ぶ。余計な欄を断ると「記録されるのはログインした本人だけ」がはっきりする（本文を受け取らない形だと、FastAPI は送られた JSON を黙って捨てるので、テストの 422 が成り立たない）
8. **承認待ちの一覧の画面を作らないこと**を仕様の写しに書くか。おすすめ：`docs/spec.md` に日付・決めた人・理由（自社 ECU 一覧の「状態」で承認待ちが分かる）を書く。理由：仕様には承認待ちの一覧があり、書かないと完了条件2「画面から一通りできる」の確かめで、画面がないと判定される
