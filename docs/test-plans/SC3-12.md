## 出典（2026-11-25 に確かめた）

- FastAPI のチュートリアル「OAuth2 with Password (and hashing), Bearer with JWT tokens」：https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/ （JWT は PyJWT、パスワードは pwdlib。無効なトークンは 401 と `WWW-Authenticate: Bearer`。存在しない利用者でもダミーのハッシュで照合して、時間の差で利用者の有無を分からせない）
- PyJWT 2.15.1：https://pypi.org/project/PyJWT/ 、変更履歴 https://pyjwt.readthedocs.io/en/stable/changelog.html （`decode` で方式を必ず指定。HMAC の短い鍵に警告。方式の取り違えの穴を 2.13.0・2.14.0 で塞いだ）
- pwdlib 0.4.2（`pwdlib[bcrypt]`）：https://pypi.org/project/pwdlib/ 、https://frankie567.github.io/pwdlib/guide/
- bcrypt 5.0.0：https://pypi.org/project/bcrypt/ （72バイトを超えるパスワードは切り捨てずに ValueError）
- パスワードの方式は計画どおり bcrypt（2026-11-25 にオーナーが決めた。FastAPI の既定は Argon2）

## 作るもの

| 場所 | 中身 |
| --- | --- |
| `POST /api/auth/login` | 本文 JSON `{email, password}`。正しければ 200 `{access_token, token_type: "bearer", expires_in}`。メールアドレスがない・パスワードが違う・無効な利用者・パスワード未設定（ロック）は、どれも同じ 401 と同じ本文（どの理由かを明かさない）。存在しない利用者でもダミーのハッシュで照合する |
| 本人確認（`app/deps.py` の `current_user`） | `Authorization: Bearer <JWT>` だけを受け付ける。署名（HS256、鍵は `JWT_SECRET_KEY`）・期限（`exp`）・利用者（`sub`＝利用者の番号）を確かめ、毎回 DB で利用者が有効かを見る。どの理由で断っても同じ 401 と `WWW-Authenticate: Bearer` |
| 仮の本人確認 `X-Dev-User-Id` | **消す**（設定 `DEV_AUTH_ENABLED`、画面の「仮のユーザー ID」も）。残すと、設定の誤りで誰にでもなりすませる入口が残る |
| 設定（`app/config.py`） | `JWT_SECRET_KEY`（SecretStr。32バイト未満なら起動しない）、`ACCESS_TOKEN_EXPIRE_MINUTES`（既定 30）。値は `.env`、AWS では SSM Parameter Store |
| ダミーデータ（`app.seed`） | `SEED_USER_PASSWORD` があれば、ダミーの利用者全員にその bcrypt のハッシュを入れる。なければ今までどおりロック（ログインできない） |
| 監査ログ | ログインの成功・失敗を残す（`login_succeeded`・`login_failed`。失敗は入力されたメールアドレスを残さず、利用者がいればその番号だけ）。パスワード・トークンは残さない |
| 画面 `/login` | メールアドレス・パスワード・「ログイン」ボタン。失敗は「メールアドレスかパスワードが違います」。成功したら一覧へ |
| 画面の全体 | ログインしていなければ `/login` へ。上にログインした人のメールアドレスと「ログアウト」。API が 401 を返したらトークンを捨てて `/login` へ。トークンは**画面のメモリだけ**に持つ（再読み込みでログインし直し） |

### オーナーに決めてほしいこと（おすすめつき）

1. **トークンを画面のどこに持つか**。おすすめ：メモリだけ（再読み込みでログインし直し）。理由：sessionStorage・localStorage に置くと、XSS（画面に差し込まれたスクリプト）で盗まれる。httpOnly の Cookie は盗まれにくいが、CSRF（他のサイトからの勝手な送信）の守りが別に要り、AWS の API Gateway（Day 16）とも合わせ直しになる
2. **ログインの成功・失敗を監査ログに残すか**。おすすめ：残す。理由：守りの決まり5は状態の変更とコメントが対象だが、不正なログインの試みを後から調べられる（TARA でいう、なりすましの検知）
3. **仮の本人確認を消すか**。おすすめ：消す（計画書の「Day 6 に JWT へ差し替え」のとおり）

### この課題では作らないもの

- ログインの回数の制限（総当たりの守り）：バックログに課題を作る（AWS では WAF などとの比較が要る）
- トークンの取り消し（ログアウトしても期限までは使える）：短い期限（30分）で抑える。設計判断に書く
- パスワードの変更・利用者の追加：Day 10（ユーザー管理）
