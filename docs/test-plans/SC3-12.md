## 出典（2026-11-25 に確かめた）

- FastAPI のチュートリアル「OAuth2 with Password (and hashing), Bearer with JWT tokens」：https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/ （JWT は PyJWT、パスワードは pwdlib。無効なトークンは 401 と `WWW-Authenticate: Bearer`。存在しない利用者でもダミーのハッシュで照合して、時間の差で利用者の有無を分からせない）
- PyJWT 2.15.1：https://pypi.org/project/PyJWT/ 、変更履歴 https://pyjwt.readthedocs.io/en/stable/changelog.html （`decode` で方式を必ず指定。HMAC の短い鍵に警告。方式の取り違えの穴を 2.13.0・2.14.0 で塞いだ）
- pwdlib 0.4.2（`pwdlib[bcrypt]`）：https://pypi.org/project/pwdlib/ 、https://frankie567.github.io/pwdlib/guide/
- bcrypt 5.0.0：https://pypi.org/project/bcrypt/ （72バイトを超えるパスワードは切り捨てずに ValueError）
- パスワードの方式は計画どおり bcrypt（2026-11-25 にオーナーが決めた。FastAPI の既定は Argon2）
- test-plan-reviewer の指摘（2026-11-25、22 件）を反映した。仕分けは最後の節

## 作るもの

| 場所 | 中身 |
| --- | --- |
| `POST /api/auth/login` | 本文 JSON `{email, password}`。正しければ 200 `{access_token, token_type: "bearer", expires_in}`。メールアドレスがない・パスワードが違う・無効な利用者・ロック（`!`）・72バイトを超えるパスワードは、どれも同じ 401 と同じ本文。**どの経路でもパスワードの照合を1回だけ行う**（ない利用者・ロック・72バイト超は、ダミーのハッシュと照合する。時間の差と 500 を防ぐ） |
| 本人確認（`app/deps.py` の `current_user`） | `Authorization: Bearer <JWT>` だけを受け付ける。`jwt.decode(..., algorithms=["HS256"], options={"require": ["exp", "sub"]})`（`exp` のないトークンを通さない）。`sub` は半角数字の文字列で 1〜18桁だけ（BIGINT に収まる）。毎回 DB で利用者が有効かを見る。どの理由で断っても**同じ 401・同じ本文**と `WWW-Authenticate: Bearer` |

| 設定（`app/config.py`） | `JWT_SECRET_KEY`（SecretStr。UTF-8 で 32バイト未満なら起動しない）、`ACCESS_TOKEN_EXPIRE_MINUTES`（既定 30） |
| 鍵の渡し方 | `.env`（オーナーが長い乱数を入れる）、`env.example` に見本の行、docker-compose.yml の API のコンテナに `JWT_SECRET_KEY` を渡す。テストは、テスト用の鍵を設定に直接入れる（`.env` の値に頼らない）。AWS では SSM Parameter Store |
| ダミーデータ（`app.seed`） | `seed(session, password=None)`：引数があれば全員にその bcrypt のハッシュ、なければ今までどおりロック。環境変数 `SEED_USER_PASSWORD` は `main()` だけで読む（テストが `.env` に左右されない）。データがすでにある DB には、別のコマンド `python -m app.seed --set-passwords` で全員のハッシュだけを入れ直す（`down -v` で消さずに済む） |
| 監査ログ | ログインの成功（`login_succeeded`、利用者の番号）・失敗（`login_failed`。いる利用者ならその番号、いなければ空）。入力されたメールアドレス・パスワード・トークンは残さない |
| 画面 `/login` | メールアドレス・パスワード・「ログイン」ボタン。失敗は「メールアドレスかパスワードが違います」 |
| 画面の全体 | ログインしていなければ `/login` へ。上にログインした人のメールアドレスと「ログアウト」。ログインの API 以外が 401 を返したら、トークンを捨てて `/login` へ。トークンは画面のメモリだけに持つ |

### オーナーに決めてほしいこと（おすすめつき）

1. **トークンを画面のどこに持つか**。おすすめ：メモリだけ（再読み込みでログインし直し）。理由：sessionStorage などに置くと XSS で盗まれる。httpOnly の Cookie は CSRF の守りが別に要り、AWS の API Gateway（Day 16）とも合わせ直しになる
2. **ログインの成功・失敗を監査ログに残すか**。おすすめ：残す（仕様 `docs/spec.md` にも書き足す）。理由：不正なログインの試みを後から調べられる（TARA でいう、なりすましの検知）
3. **仮の本人確認を消すか**。おすすめ：消す（計画書の「Day 6 に JWT へ差し替え」のとおり）
4. **API の説明の画面（`/docs`・`/openapi.json`）を、ログインなしで見せるか**。おすすめ：手元では見せたまま、AWS（Day 13）の前に決め直す（バックログの課題にする）。理由：データは含まず、手元で API を試すのに使う。公開の環境で出すかは別の判断

### この課題では作らないもの

- ログインの回数の制限（総当たりの守り）：バックログに課題を作る
- トークンの取り消し（ログアウトしても期限までは使える）：短い期限（30分）で抑える。設計判断に書く
- パスワードの変更・利用者の追加：Day 10（ユーザー管理）
