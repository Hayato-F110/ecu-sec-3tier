ストーリーを進めます。課題：$ARGUMENTS

## 1. 読む

- `getJiraIssue` で課題の説明・完了条件を読む。Jira で「進行中」にし、開始日を今日にする
- `docs/spec.md` の関係する節（役割と権限・画面・テーブル・承認フロー）と、`docs/schedule.md` のその日の完了条件
- 使う技術の最新の公式ドキュメント（版は `backend/pyproject.toml`・`frontend/package.json` の版に合わせる）。出典を控える

## 2. 設計案（Plan モード）

`EnterPlanMode` で、次を短く出す。

- 何を作るか（API のパスと役割ごとの可否、テーブルの変更、画面）
- **守りの決まり**（CLAUDE.md「このシステムの守りの決まり」）のどれに関わるか。特に：会社での絞り込み、他社は 404、状態の変更の検証、職務分離、監査ログ
- テストの一覧（表。列は「確かめること｜テストの置き場所｜確かめない範囲（理由）」）。**API を足すなら、他社のユーザーで呼んで 404 になる行を必ず入れる**
- 主な設計判断と、採らなかったら何が起きるか（スプリントの最後の `/design-decisions` の材料）
- 守りに関わる課題（CLAUDE.md「進め方」の、レビューを2回までにする変更と同じ範囲）は、テストの一覧を `docs/test-plans/<課題キー>.md` に書き、サブエージェント `test-plan-reviewer` に初見で突き合わせてもらってからオーナーに出す

オーナーの承認をもらう（承認の前に実装しない）。

## 3. テストを先に書く

- 承認された一覧のとおりにテストを書き、**実装の前に流して、新しいテストが落ちる（赤）ことを確かめる**。どれが落ちたかを PR に書く
- 実装の前に通ってしまうテストは、新しい振る舞いを確かめていない印なので、実装に進まずにテストを直す
- 今ある実装にあとから足すテストは、実装をわざと壊して落ちるかを確かめる

## 4. 実装する

- 小さく進め、テストを緑にする。テストを実装に合わせて弱めない
- 数値・設定（トークンの有効期限など）は設定（`backend/app/config.py` など）に集め、コードに直書きしない
- 秘密情報は `.env`（ローカル）・SSM Parameter Store（AWS）から読む

## 5. 確かめてコミット・PR

- 静的解析と関係するテスト → 全体の検査（裏で動かす）→ 画面・API を実際に動かして確かめる（`docker compose up -d` と、ブラウザか `/docs`）
- `/commit` でコミット。コードを変える PR は、出す前に `/code-review` を呼び（回数は CLAUDE.md「進め方」。PR の中身で1回か2回まで）、指摘を「直す／直さない（理由）」に仕分けて PR の説明に書く。最後の回のあとに直したときは「## 直しの証拠の表」を書く
- PR の説明：完了条件ごとの証拠の表、赤から緑になったテスト、確かめた画面・API の結果
- データ分離・認可に関わる変更は、PR の前にサブエージェント `security-reviewer` にも見てもらう
