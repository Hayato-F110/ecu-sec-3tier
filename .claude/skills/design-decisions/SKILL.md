スプリント $ARGUMENTS の設計判断を説明します。

1. `docs/design-decisions.md` の「予定している判断」（計画書 第8章の表）から、このスプリントの行を取り出す。このスプリントで途中で変えた判断・新しく決めた判断も、devlog・PR・会話から拾って足す
2. 判断ごとに、次の形で書く（1つあたり画面の半分まで）
   - **判断**：1行
   - **実際のコード**：その判断が表れている `ファイル:行` と、要の数行の引用
   - **採らなかったら何が起きるか**：具体的な攻撃・事故の手順で（例：「URL の ECU の ID を 1 つずつ変えて GET すると、他社の対策状況が読める」）。できれば、**その判断を外すと落ちるテスト**の名前を添える（なければ「テストなし」と書き、足すかをオーナーに聞く）
   - **車載ソフト開発に例えると**：1行（例：職務分離 → 設計者とレビューアの分離、版を上書きしない → リリースしたソフトの版管理）
   - **ISO/SAE 21434・TARA との対応**：あれば一言
3. このスプリントで判断を変えた・やめたものは、元の行を消さず「変更：日付・理由」を足す
4. 書いた内容をオーナーに見せ、説明できるか確かめる問いは出さない（オーナーは答えを読んで理解する）。分かりにくい所があれば聞いてもらう
5. `docs/design-decisions.md` の変更をコミットに含める（その日の devlog の PR と一緒でよい）。PR は `[PR #番号](https://github.com/Hayato-F110/ecu-sec-3tier/pull/番号)` のリンクで書く（ファイルでは `#番号` が自動でリンクにならないため。2026-11-28 にオーナーが決めた）
